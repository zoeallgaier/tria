## Share profile — FIXED, and postLink had the same bug

`shareProfile()` (`app.js:8250`) is wired from all three places the plan
mentions checking: your own profile's ••• sheet, a visitor's ••• sheet, and the
friend tie menu. It calls `profileLink()` (`app.js:8236`), which builds the link
off `/^https?:/.test(location.origin)`.

**Confirmed the bug, then fixed it.** Capacitor's default iOS scheme is
`capacitor://localhost`, not `http:`/`https:` — nothing in
`capacitor.config.json` overrides it. So inside the App Store build,
`location.origin` failed the regex and `profileLink` fell back to a bare
`@username` with **no link at all** — the share sheet or clipboard copy handed
over plain text, silently. `profileLink` now falls back to
`https://triaonline.com/` (the CNAME target per `index.html`'s `og:url`) instead
of a bare handle when `location.origin` isn't http(s), still preferring the real
origin when one exists (local dev, the website).

**`postLink()` (`app.js:8574`, the post's own ••• → Copy link) had the identical
bug** and was still unfixed as of a repo sweep for every share/share-profile
call site: same regex, same bare-`@handle` fallback with no URL. Patched the
same way, mirroring `profileLink` exactly. Every call site that shares or
copies a link — both profile ••• menus, the friend tie menu, the post •••'s
Copy link, and the report payload that carries a post's link — now always
produces a real, openable `https://triaonline.com/#/...` URL inside the app,
not just on the web.

**Verified:** headless boot pass clean (zero console/page errors), grepped the
synced bundle (`ios/App/App/public/js/app.js`) for both fixed fallbacks, built
and launched on the iPhone 17 Pro simulator — the ••• sheet renders "Share
profile" correctly with no regression. Not verified: an actual on-device tap of
Share profile followed by opening the resulting link from outside the app (no
tap-automation tool — idb/cliclick — was available in this pass). Worth a manual
check on Zoe's phone: tap Share profile, send the link somewhere, open it cold,
confirm it lands on `#/u/<name>` rather than Discover.

## Repost icon options

Current glyph is `ICONS.repost` (`app.js` inside the `ICONS` table, the
`repost:` entry) — a circle broken at two points with true chevron arrowheads
rotated onto the tangent, deliberately *not* the squared two-arrow shape other
apps use ("Tria's corner scale has nothing that shape belongs to") and
deliberately not axis-aligned brackets (reserved for pull-to-refresh, so a mark
on a card that read as "reload this" would be worse than no mark). It renders
at two scales: the card row (`.card-repost svg`, `transform: scale(0.88)`,
`css/app.css:2035`) and the action-sheet row (`openGlyphMenu`/`openSheet`,
plain `svgIcon('repost')`). Only one glyph exists — a reposted card just
recolors it to the original post's type colour via `.reposted` (`color:
var(--burst, ...)`, `css/app.css:2058`); there's no second drawn state to
replace, which keeps the redesign to one path.

Zoe's read — "arrows are a little funky" — most likely means the chevron
terminations read busy at the card's 18-20px render size, where the two short
angled strokes per arrowhead compete with the circle's own curvature.

**Step:** mock up 4-6 alternatives as an Artifact, rendered at both the card
scale and the sheet-row scale so the pick isn't made blind to where it's
smallest. Stay inside the standing constraints: line glyph, `stroke-width:
1.8`, not the squared two-arrow convention, not axis-aligned brackets. Worth
trying: fewer/plainer terminal marks on the same broken-circle shape, a
looped/infinity-style circulation mark, two offset arcs with a single small
arrowhead each rather than a full chevron. This is a design pick, not a code
change — hold the actual `ICONS.repost` edit until Zoe has chosen.

## Haptics — audit

The house rule (`app.js` haptics block, restated in
[ios-shell.md](ios-shell.md)): **only an act that changes the shared world**
gets a buzz — a like, a vote, an RSVP, a comment, a repost, a published post —
never an act that only changes what you're looking at (a filter, a disclosure
panel). LIGHT for something that stays on screen, MEDIUM for something that
lands in the real world. A `danger` sheet row is the one exception that fires on
the *touch* rather than the confirmed write, because it's a warning about what's
coming, not a receipt.

**Already covered**, confirmed by reading each site — no work needed:
going/not-going (`app.js:4095`, `4128`), the like heart (`app.js:4345`, fired on
the optimistic flip rather than the server reply — a deliberate, documented
exception to "on the confirmed write"), poll vote, a comment send
(`app.js:7685`), repost/undo-repost (`app.js:8587`, `8594`), any danger sheet
row — delete, block, report (`app.js:5396`, `8321`), publish success/error
(`app.js:12438`, `12448`, `12489`, `12493`).

**Correctly silent, per the rule — leave alone:** the filter dial, every
disclosure panel (comments/who-liked/who's-going), pull-to-refresh, tab
switches, page navigation. These were deliberately pulled in 1.3 (see
[ios-shell.md](ios-shell.md)) because every fire-and-forget haptic call is a
round trip through the Capacitor bridge that lands on the main thread mid-scroll
— re-adding one of these needs a real argument against a specific *fixed* panel,
not a blanket "more feels responsive."

**Gaps — go/veto pass done, wired:**
- **Friend request accept** (Updates' request row, `wireRequests` in app.js) —
  go, LIGHT, gated on the write actually succeeding (matches the poll-vote/
  toggle-going convention of firing only on a confirmed non-throw result).
- **Friend request ignore/decline** (same function) — go, plain LIGHT (not the
  danger/touch-fire treatment; Zoe read it as a normal confirm, not a warning).
- **Add friend / cancel request / unfollow**, both the profile tie button and
  the Friends-list row tie (`wireTieList`) — go, LIGHT at all three sites, same
  success-gating.
- **Private account toggle** on Edit profile — go, but scoped: LIGHT fires on
  Save's confirmed write only when the switch's value actually changed from
  what it loaded with, not on every plain name/bio save. It was already true
  that this control commits on Save rather than on the tap (see below), so the
  gating point was Save succeeding, not the toggle itself.
- **Pin/unpin a post** — WIRED, with pins (2026-09-03). LIGHT on the confirmed
  write for pin, unpin, reorder and swap. Two things the rule decided that were
  not obvious in advance: the DRAG LIFT gets nothing (it changes only what you
  are looking at, and the card visibly rising says so), and the pin that follows
  a publish is silent, because SUCCESS then LIGHT is one act reported twice.

Everything else scanned (comment send, votes, likes, reposts, publish, danger
rows) already fires. This list was short because most of the app already
followed the rule.

## Pinned profile cards — BUILT (2026-09-03)

Up to three cards a person holds above their own wall: a post of theirs, or a
song. Zoe's calls, all four taken as given and all four built — **three slots**,
**song / new post / existing post**, **"pin post" in the post's glyph menu**,
**drag to reorder**, **activities allowed**.

**What shipped.** `users.pinned` (`supabase/add-pins.sql`) holding an ordered
jsonb array; `pinsSectionHtml` / `pinCardEl` / `wirePinDrag` in app.js render and
edit it, between the identity block and `#feed` in `renderUser`; `Store.setPins`
writes it. Three ways to fill a slot, because the ask named three:
`#/pin/song` (the listening picker, aimed somewhere else), `#/pin/post` (your own
posts as rows), and "Write something new", which sets `pendingPin` and pins what
the composer publishes. All three hang off **Pin to profile in your own
profile's •••**, beside Edit profile. `openPostMenu` gained one row that flips
between "Pin to profile" and "Unpin from profile".

**Zoe's pass, same day, and it took away more than it added.** The first build
carried a caption over the stack ("Pinned · hold to reorder"), a type word over
each title (Song / Note / Frame), a pastel tile with the type's glyph on any post
with no picture, and a dashed empty-slot tile inviting a third pin. All four are
gone, and the reason is one reason: a card is already a card, and every one of
them was the page explaining its own furniture on the one screen that is supposed
to be about a person. The cards also got their width back — they had `--inset` of
their own on top of the view's, which made the page's headline the narrowest
thing on it. And the album bloom was spilling into the card's square corners,
which is a WebKit compositing fact rather than a CSS mistake; see design.md.
Losing the empty tile cost the only surface a SONG pin could be started from,
which is why the way in moved into the profile ••• rather than simply
disappearing.

**The proposed `pinned_items` table lost to a jsonb array, and the reorder is
why.** The argument for a table was that ordering and the three-slot cap belong
in SQL. Building the drag turned it around: a `position` column wants
`unique(user_id, position)`, and swapping two rows under that constraint needs
deferred constraints or a three-step shuffle through a temporary value, where an
array simply has no such thing as two things in slot 1 and a reorder is ONE write
of the whole list. The cap is still in SQL and is stronger there — a check on
`jsonb_array_length` cannot be raced by two inserts — and the column costs no
read, where a new table would be a round trip on every world load for at most
three rows a person. Full reasoning in the migration's own header.

**The open questions, answered:**

- **Does a pin duplicate the post below?** Yes, both. A pin is a spotlight, not a
  move — taking the post out of chronology would make the profile quietly lie
  about when things happened, and a reader who scrolled past the card at the top
  has no way to know that is why the post isn't where they expected it. Flipping
  it is a one-line filter in `renderUser`'s `list` if Zoe wants the other
  behaviour.
- **Can a pin be reordered?** Drag, and a Move up / Move down pair in each card's
  own •••. The pair is not a fallback for a fussy gesture: it is the only way to
  reorder with a keyboard, and the only thing that says out loud that the three
  are ordered.
- **Do pinned activities make sense?** Zoe said yes, so they are pinnable, and
  they meet the same friends-only courtesy on the way out that the wall already
  applies to them. (Dailies exclude activities because answering a prompt with a
  plan makes no sense, not because an activity is unfit to be looked at.)
- **Does a song pin reuse the Find flow or need its own form?** Neither: it reuses
  the LISTENING picker, which already searches iTunes, reads a pasted Spotify or
  Apple link, dedupes by title+artist and debounces for the rate limit.
  `renderListening(mode, at)` takes a mode and a slot; the only differences are
  the words at the top, where the chevron aims, and which writer the pick is
  handed to. A song pin stores `listening_to`'s object minus `at` — a status
  expires, a choice doesn't.

**Album covers got the extra**, which was the one thing the ask singled out. The
sleeve is treated as an object rather than as content: a drop shadow and a lit
top edge instead of a hairline, one diagonal sheen, and a blurred blown-up copy
of the artwork blooming across the card and masked out before it reaches the
words. The blur is what makes it free — hotlinked artwork can be blurred by CSS
but not read by canvas, so the card wears the record's colour with no colour
column, no sampler and no second request. See [design.md](design.md).

**The haptics row this file deferred is now wired.** Pin, unpin, reorder and swap
all fire LIGHT on the confirmed write; the DRAG LIFT deliberately fires nothing,
because lifting a card changes only what you are looking at and the card visibly
rising already says so. The one exception is the pin that follows a publish,
which is silent: SUCCESS and then a LIGHT 200ms later is one act reported twice.

**Nothing native.** `PAGE_SEL` is still four selectors — a pin card is content
with a stretched link, its ••• raises the same sheet the post card's ••• does,
and neither of the two pickers holds a caret that sits on the keyboard. The
question this file asks about every item ("does it need to be DRAWN by UIKit, or
CALLED through it?") answers no twice here.

**Verified:** headless boot pass clean on every new surface (a profile with three
pins, with one, with none, a visitor's, both pickers), in Chromium AND in
Playwright's **WebKit**, which turned out to be worth having: it reproduces the
bloom's corner spill that Chromium does not, so a compositing bug that used to
need a 60-second simulator build is now a 4-second run. Plus a scripted pass over
the drag (a long-press lift, the neighbour displacing, the committed array), the
card menu, the post menu's flipping row, the swap-at-three sheet, and
compose-to-pin end to end — all with zero console or page errors. Built and
launched on the iPhone 17 Pro simulator and looked at on the real build with the
native chrome up (a temporary probe in the generated bundle, removed by
`ios-sync.sh` afterwards): the stack, the type squares and the album bloom all
render correctly in WebKit, mask included. **Not verified: an actual finger.** The
drag was driven by synthesised pointer events in Chromium, and the thing that can
only be judged on a phone is the 280ms lift threshold — whether it feels like a
deliberate pick-up or like the page snagging on a scroll.

**`supabase/add-pins.sql` HAS NOT BEEN RUN** (probed read-only 2026-09-03:
`users.pinned` answers `400 42703`). Until it does, the feature is inert exactly
as [data.md](data.md) describes: no reader has pins, the add tile still offers
itself on your own profile, and the first save says "Pinned cards aren't set up
on this server yet." It is the only pending migration in the tree.

## More Discover cards

**SETTLED, 2026-09-03: Discover gets ONE scheduled card, and the stack was
tried and taken back out.**

The question this section opened with — does the single card slot become a
stack? — got answered by building the stack and then living with it for a day.
Manifest Monday shipped as a second, smaller card under Monday's Daily. It
worked; nothing about it was broken. What it revealed is that the cost of a
Discover fixture is not measured in whether the fixture is good, it is measured
in **how far down the grid goes.**

Discover is a meeting ground, and the grid of what people actually made is the
meeting. The Daily card, a second card, and the listening rail together pushed
that grid clean off the first screen. Zoe's call, on seeing it: *"I don't want
more than one card on the discover. With all three of these additions it covers
real users' content which we dont want."*

So the rule for everything below:

- **One scheduled card.** A holiday daily REPLACES that day's rotation entry
  rather than stacking beside it. Same card, different question — which was
  always the simpler of the two options this section originally offered.
- **A rail is not a card.** Listening To is per-person, so it earns a strip of
  small squares rather than a headline; it costs the height of a chip instead of
  the height of a card. That distinction is the only reason two fixtures can
  coexist above the grid at all.
- **The thing to weigh for any future addition** is not whether the idea is good
  but what it costs the grid. That is the cost that got paid here, and it is the
  one that is easy to forget while the idea is still an idea.

The rule is restated in app.js above `lastDailyFor`, which is where somebody
adding the next card will actually be standing.

### Holiday-specific dailies

The existing rotation (`DAILIES`, `app.js:8941`, and `dailyOn`, `app.js:9114`)
is **pure weekday modulo**: `DAILIES[day % DAILIES.length]`, chosen specifically
so "every prompt keeps the same weekday forever" (70 = 10×7, explicitly
load-bearing per the comment above the array). A holiday is a **calendar date**
(Oct 31 lands on a different weekday every year), so it cannot be inserted into
`DAILIES` as a row — it needs a date-keyed override checked *before* the modulo
lookup: something like a small `HOLIDAY_DAILIES` list keyed by `'MM-DD'`,
consulted first in `dailyOn(day)`, falling through to the regular rotation on
every other date. Answers still file the same way (`daily-<slug>` tag), so
`dailyForPost`, `dailyAnswers` etc. need no change — only `dailyOn` gains a
branch.

Open question: does a holiday daily replace that day's regular rotation slot for
everyone permanently (so `lastDailyFor` on a re-run of that weekday skips it,
the way a leap in the array would), or does the regular rotation just pause for
one day and resume exactly where it left off? The second is simpler and matches
"the pattern dissolves" warning already in the code — a skip is cleaner than a
shift.

### "Listening to" — BUILT (2026-09-03)

Zoe's calls: a **rail of everyone's** on Discover with your own square first;
**search, with paste as a fallback**; **auto-clear after 7 days**. No account is
connected to anything.

**What shipped.** `users.listening_to jsonb` (`supabase/add-listening-to.sql`,
folded into `schema.sql`) holding `{title, artist?, art?, url?, at}`. The rail is
`nowPlayingEl` in app.js, between the day's cards and the trending tags; the
picker is a page at `#/listening` (`renderListening`); the writer is
`Store.setListeningTo`. The 7-day expiry is enforced on the READ, in `freshSong`
in store.js, so nothing stale can render even for a day — a nightly sweep
couldn't promise that.

**The three questions, answered by measurement rather than by reading docs:**

**1. "Links should lead to the user's default music app."** There is no such
thing on iOS. Default browser and default mail are settings; default music is
not, and no API can ask. What works is the **universal link**: `music.apple.com`
opens the Apple Music app when it's installed, `open.spotify.com` opens Spotify,
and neither needs an integration of any kind.

**But not through `@capacitor/browser`.** That's SFSafariViewController, which
deliberately does NOT follow a universal link into the app owning the domain —
so a song opened the old way is always the web player in an in-app sheet. The
fix is `UIApplication.shared.open`, added as `openExternal` on
`TriaSettingsPlugin` (the class was already making exactly that call for
Settings). app.js's outbound handler now reads `data-out="system"` on the anchor
to choose between the two, falling back to the sheet if the plugin predates the
method. See [ios-shell.md](ios-shell.md).

**2. Album art, automatically.** Yes, free, no account, verified live:

- **iTunes Search API** (`itunes.apple.com/search`) — no key, no auth, and it
  answers `access-control-allow-origin: *`, so the webview calls it directly. One
  request returns canonical title, artist, artwork and a `music.apple.com` link.
  Artwork sizes in the URL PATH (`100x100bb` → `300x300bb`), so a bigger copy is
  a string edit and not a second request. `itunes.apple.com/lookup?id=` takes the
  `?i=` track id off a pasted Apple Music link and returns the same row.
  Rate-limited around 20/min per IP, hence the 320ms debounce. Results are
  DEDUPED by title+artist and the limit raised to 25 to pay for it: iTunes ranks
  across every release, so "midnight city" came back with the M83 track twice and
  four identical compilation rows.
- **Spotify oEmbed** (`open.spotify.com/oembed?url=`) — public, keyless, CORS
  `*`, returns a title and 300px artwork. This is the ONLY part of Spotify's API
  that needs no token, and it is what makes the paste fallback work.

**3. Spotify, properly (the SwiftUI article Zoe linked).** That article is the
Authorization Code / user-login flow, which is for reading what someone is
actually playing — the thing we decided not to do. Album art needs no user login
at all. The relevant flow is **Client Credentials**: no user ever signs in, and
`/v1/search` would give real search, artist, 640px art and a genuine Spotify
link. Measured facts:
- Every `/v1` endpoint 401s without a token, and a token needs a
  `client_secret`. `js/config.js` is "safe to commit" and the bundle is readable
  by anyone who unzips the .ipa, so the secret cannot ship — the exchange has to
  run server-side.
- That is NOT new infrastructure: `supabase/functions/push` already exists, so
  it's a second Edge Function of the same shape (~60 lines of Deno, an hourly
  cached token, the secret in Supabase's env).
- Spotify's own API is fully browser-callable (it echoes Origin and allows
  credentials), so the proxy exists only to hold the secret.
- Not done, deliberately. It changes only where search results come from; the
  stored shape doesn't move, so it stays a contained follow-up.
- **Odesli / song.link**, the obvious "one link, every service" answer, now
  **401s without an API key**. It used to be free. That option is gone.

**Red flags, and where each landed:**
- *Staleness* — solved by `at` + the 7-day read filter.
- *The ethos risk*: a live strip of what everyone is playing is the ambient
  check-back loop Tria is built against. Mitigated by never updating live — the
  rail repaints when the page does, and there is no badge (house rule anyway).
- *Privacy shape*: this is the first thing about a person that is NOT
  audience-gated. It sits on `users`, so `can_view_post` and the private-account
  fence don't reach it and any signed-in reader sees it, exactly as a name and
  bio already are. Called out in the migration's own comment.
- *Preview audio*: the iTunes response carries a 30s `previewUrl`. Left alone —
  it's autoplay-adjacent and a whole player surface.
- *Artwork is hotlinked*, never re-hosted: Apple's Search API terms cover
  DISPLAYING artwork beside a link to the store, which is not the same permission
  as copying it into our own bucket.

**Migration is run** (confirmed over PostgREST, `200 []` against a bogus-column
control returning `400 42703`), so the feature is live end to end.

**The link belonged to whoever SET it. FIXED 2026-09-03, at the reading end.**
The wart was that a song added by search carries a `music.apple.com` link, so a
Spotify listener tapping it landed in Apple Music (or, worse, a web player
selling them a second subscription); a pasted Spotify link opened Spotify for
everyone. No keyless way exists to make ONE link adapt per viewer — that is
exactly what Odesli did before it went behind a key — so the link is chosen per
READER instead:

- **The song stores a link per service.** `{apple?, spotify?}` replaces the
  single `url`; usually only one is known. Pre-fix rows are folded by hostname
  on the read (`freshSong`), not migrated: jsonb takes both shapes and every row
  expires within a week anyway.
- **The reader's service is inferred, not asked.** `TriaSettings.musicApps`
  answers `canOpenURL("spotify://")`. Having gone and installed Spotify is a
  better signal than a modal interrupting the tap, and Apple Music ships
  preinstalled so its presence says nothing — the ABSENCE of Spotify is the
  signal. Needs `spotify` in `LSApplicationQueriesSchemes`, which fails safe.
- **A missing exact link degrades to a SEARCH url in the wanted service.**
  `open.spotify.com/search/<title artist>` and `music.apple.com/search?term=`
  are both claimed by their apps, so the tap still lands in the right app, one
  row short of the right track. That is a much smaller failure than the one it
  replaces, and it is why this needs no server and no secret.
- **`Open songs in` on the profile editor** (Automatic / Apple Music / Spotify)
  covers the one case the guess gets wrong: both installed, Apple preferred.
  Per-DEVICE in `localStorage`, never in the users table — which service you pay
  for is nobody else's row — and it lands on tap rather than waiting for Save,
  since it isn't part of the profile being edited.

**Confirmed on device 2026-09-03**, which is the only place it could be: a
simulator cannot install Spotify, so `canOpenURL` always answers false there and
Automatic always resolves to Apple Music. On a phone with Spotify installed the
inference reads it and the tap lands in the app rather than a web player.

The rejected shape was a **one-time popup on the first music tap**. It asks at
the only moment the question is understandable, which is a real argument, but it
puts a modal between "I tapped a song" and hearing it, and the inference makes
it unnecessary for nearly everyone.

**Tier 2 is still the Spotify Client-Credentials proxy** described above, and it
now drops in cleanly: it would replace a search URL with an exact link inside
`songLink` and change nothing else. Worth verifying Spotify's Search endpoint is
still available to newly registered apps before committing to it — several `/v1`
endpoints were restricted for new apps in late 2024.

**Also not built:** a line on the identity card. The rail was the choice; the
profile line is a natural companion and a small follow-up.

### Manifest Monday — BUILT, THEN REMOVED (both on 2026-09-03)

Shipped as a second, smaller card under Monday's Daily, asking "What are you
manifesting this week?", on its own weekly epoch. It worked: verified against
1,200 days of calendar (`day % 7 === 6` matches every Monday and nothing else,
across both DST transitions), and it proved that two native `.daily-answer`
buttons coexist correctly — `pageSpec` stamps a unique id per element and Swift
keys its button dictionary off it, so no native change was needed.

**Then it came out, and it came out for the page rather than for itself.** See
the settled rule at the top of this section: two cards plus the listening rail
pushed Discover's grid off the first screen, and the grid is the point of
Discover. Nothing was wrong with the feature. The cost was the fixture.

**Removed cleanly**, which meant more than deleting the occurrence: the `kicker`
and `compact` options on `dailyCardEl` went with it (a parameter whose only
caller is gone is a shape the next reader has to reverse-engineer),
`.daily-card--sub` went from app.css, `dailyForPost` and `lastDailyFor` lost
their branches, Discover's paint went back to one card and one button handler,
and the `dailyLabel(slug)` helper went too — with one card it could only ever
return `'Daily'`, and a function with one possible answer is worse than the
literal it replaced. What was KEPT is the capitalisation it introduced: **Daily**
is capitalised everywhere it names the feature, because that is its name and not
an adjective. If a holiday daily later wants its own name on the card, a helper
like `dailyLabel` is the right shape to bring back — it was not wrong, just
unused.

**What the exercise was worth**, since it did not ship: the calendar arithmetic
is proven, the two-native-CTA question is answered, and the one-card rule now
exists as a rule with a reason behind it rather than an unexamined default. The
last of those is the useful one — it is what holiday dailies get built against.

## What's not in this doc

Nothing here touches the two chrome docs
([native-chrome.md](native-chrome.md), [design.md](design.md)) directly — none
of these six items are native-chrome surfaces by the existing `PAGE_SEL`/glyph
rules (a pinned card's own controls, a Listening To link, are content and
disclosure-panel-shaped, not one of the four closed PRIMARY ACTS). If any of
them turn out to need a native control as they're built, that's a scope change
worth flagging before writing it, not after.

**That happened once, and the prediction above was right about the wrong
thing.** Listening To needed no native CONTROL — the rail is content, `PAGE_SEL`
is untouched and still four selectors. What it needed was a native CAPABILITY: a
universal link cannot reach Apple Music or Spotify through
SFSafariViewController, so `openExternal` went onto `TriaSettingsPlugin` (see
the Listening To section above and [ios-shell.md](ios-shell.md)). Flagged before
it was written, as the rule asks. **It happened a second time on the same
feature**: picking the link per reader needed `musicApps`, because only UIKit can
answer what is installed. Same shape, same plugin, still no new control. The
lesson for the remaining items is that
"does this need native?" has two answers worth asking separately: whether
something has to be DRAWN by UIKit, and whether something has to be CALLED
through it.
